## reforce changes made in M7a (from this suite)

- **Line width** (#16): area-based widths (column integral / 255, which counts antialiased edge pixels fractionally) are 2.836 px per LWdt at 1980x1260 and 5.165 px per LWdt at 3456x2234 (run 6, full screen), exactly proportional to LWdt at each size. Counting lit pixels gives 3 and ~5 px (the probe table's 3,9,15,21,27 and 6,14,26,38,46) because each edge adds a partial pixel; neither H/420 (3.0 / 5.32) nor round(H/420) (3 / 5) matches the areas. reforce now uses LWdt x (H - 68) / 420 (2.838 / 5.157 px per LWdt; was H / 420). Two sizes cannot tell whether G-Force scales with H, W or both.
- **Line width vs frame size** (#38, F6): run 24 resized G-Force's window to 17 sizes (plus full screen): px per LWdt = 0.733 + 8.67e-4 min(W, H) + 5.10e-4 max(W, H) on G-Force's frame (max error 0.0005), and G-Force renders frames above ~5.2 MP at half size with doubled pixels, so 3456x2234 full screen is 2 x s(1728, 1117) = 5.165. The (H - 68) / 420 line went through 1980x1260 and that half-size frame. reforce uses this law (`reforce.LineScale = gforce`, default; `frame` applies it to the render size).
- **Dots off the pixel grid** (#3): G-Force draws the x = -1 dot of `X0 = 2s-1` (half visible) but no dot at x = +1. reforce now skips unconnected dots whose center is outside [0, W) x [0, H).
- **Frame order** (#1/#13, run 1 shot 6): with a FlowField and a WaveShape cut in the same script call, G-Force flows the old WaveShape's last frame once more with the old field (the frozen zoom-out rings have no ring at r = .5) and does not move the new WaveShape's first frame. G-Force runs script commands between a frame's flow pass and its draw; reforce now applies FlowField/Union switches one step after they are issued (ctest `reforce_frame_order_render`).
- New command `morph:LAYER:SECS:NAME` (explicit morph duration, 0 = cut) so scripted `StartConfig(type, name, secs)` / `SetFlowField(name, union, secs)` replay exactly.

## Remaining gaps

- #10 mid-morph: stripe angle left: G-Force -22.3, reforce -24.9; mid-morph: stripe angle right: G-Force -22.2, reforce -24.8. At mid-morph G-Force's trails look like reforce's ~0.13 s (1.3 %) earlier in the 10 s FlowField morph (reforce reproduces G-Force's angle with the morph started 0.13-0.15 s later). Both end states match, and the dark-center width agrees. Consistent with G-Force starting a FlowField morph only after its threaded field build, or with FlowField.Transition.Duration.Deviation (0.02) applying to scripted morphs too; one shot cannot tell. reforce keeps the exact scripted timing.
- #19 run4 age 15.00 s: G-Force 20, reforce 17. The fade-out tail is 3 levels brighter in G-Force: its fade-out (and only the fade-out; the fade-in matches at 60 fps) starts ~0.07 s (4 frames) after spawn + 6 + PDur. Run 4's three fade-out points all fit a 0.07 s later start (198/93/19 vs G-Force 197/93/20); reforce keeps the probe #19 model.
- #34 run17: decay per frame: G-Force 2.0, reforce 1.0; run18: decay per frame: G-Force 2.0, reforce 1.0. G-Force loses 2 levels per frame on a pure 1-px translation (reforce 1): its source coordinate lands 1/1980 px short (pixel = (x + 1) / 2 x (W - 1), corner-aligned: probe finding #26), so the 1/16-px bilinear weights take 1/16 of the older neighbor and the truncation drops a level every frame.
- G-Force's effective frame rate (above) is not emulated: reforce runs its simulation at exactly `Graphics.TargetFrameRate`, so trails and B-var counters advance ~8 % faster per second than in G-Force on this machine (decay 60 vs ~55 levels/s at 60 fps).
- Not covered here: sprites (run 5 is not replayed), the Union end-of-transition jump, line width at sizes other than 1260 and 2234 px tall.
